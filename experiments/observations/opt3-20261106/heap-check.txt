# Reading:
# - Both plans finish in a 1 GiB JVM; the final plan has the BroadcastHashJoin LeftOuter BuildRight only with the hint.
# - With the hint, Spark's MemoryStore can't keep the broadcast value in memory: "Not enough space to cache
#   broadcast_11 in memory! (computed 215.9 MiB so far)" in both rounds, so it goes to disk (MEMORY_AND_DISK). Storage
#   memory in a 1 GiB JVM is at most (1024 - 300) x 0.6 = 434 MiB, shared with execution. PLAIN logs no such warning.
# - G1 Old Gen peaks at 922-930 MiB with the hint vs 700-728 MiB without (about +200 MiB, the relation's size).
#   peak_used_sampled is near the heap size in both (G1 fills the heap before it collects), so it isn't informative.
#   The heap live after a full GC once the write is done is the same (195 vs 191 MiB): the relation isn't retained.
# - The Docker cluster splits the roles: the driver (master container, 1 GiB) builds the relation and keeps it in its
#   block manager, and each executor (1 GiB, 2 task slots) deserializes one copy for its tasks. Each JVM holds one
#   copy at a time, as here, but expect the same disk fallback in each.
