# MapReduce Worked Example, the Shuffle Phase, and the Combiner

> **Source:** `ComPar-Lec03.pdf`, printed slides 36–41 ("Map-Reduce example (1)", "(2)", "(2) with Combiner", "The Shuffle Phase", "Extended programming model") · **Back to:** [index](../index.md)

## The example: count occurrences of each destination node (in-degree)
Input = (k1, v1) edge pairs (source, destination), split into two blocks:

| Block 1 | Block 2 |
|---|---|
| (A,B) (A,C) (A,D) (B,E) (B,D) (C,B) | (C,D) (C,A) (D,A) (E,C) (E,B) (E,D) |

**Map:** for each `(src, dst)`, emit `(dst, 1)`.

| Mapper 1 emits (k2, v2) | Mapper 2 emits (k2, v2) |
|---|---|
| (B,1) (C,1) (D,1) (E,1) (D,1) (B,1) | (D,1) (A,1) (A,1) (C,1) (B,1) (D,1) |

## Example (1): Partition → Shuffle → Sort → Reduce
1. **Partition / Shuffle / Sort** groups the values by key into (k2, [v2]) lists.
2. **Two reducers** process the groups.
3. Output (k3, v3):

| Group (k2,[v2]) as shown on slide | Output (k3,v3) |
|---|---|
| (A,[2]) | (A,2) |
| (B,[2,1]) | (B,3) |
| (C,[1,1]) | (C,2) |
| (D,[2,2]) | (D,4) |
| (E,[1]) | (E,1) |

(The slide's grouped lists show *pre-combined* values such as `[2,1]`, matching the combiner version below. Without a combiner the lists would be all 1s, e.g. B → [1,1,1].)

Mapper output and reducer output go to **local storage** (intermediate files on the mapper's local disk; final output to the DFS).

## Example (2): shuffle routes keys to reducers
The same pipeline, showing that the shuffle sends a **subset of keys to each reducer** (by partition function):
- Reducer 1 gets A, C, E → (A,2), (C,2), (E,1)
- Reducer 2 gets B, D → (B,3), (D,4)

## The shuffle phase: the hidden cost of MapReduce
**All-to-all network communication.** The shuffle is automatic but expensive: every mapper output must be transferred to the correct reducer over the network.

| Step | What happens |
|---|---|
| **1. Partition** | Each mapper assigns each emitted key to a reducer using a **partition function (default: `hash(key) mod R`)**. This controls which reducer gets which key. |
| **2. Spill to disk** | Mapper output is **sorted in memory** (in-memory buffer). When the buffer fills, it **spills to local disk**. Multiple spills are merged (**external merge-sort**). |
| **3. Copy (shuffle)** | Each reducer **fetches its partitioned data from all mappers** over the network. This is the all-to-all transfer step and is **network-I/O bound**. |
| **4. Merge & sort** | The reducer merges the fetched data (already sorted per mapper) using a **k-way merge**. Result: globally sorted key-value pairs ready for `reduce()`. |

**Spark's key innovation:** avoid this disk I/O by **keeping intermediate data in memory**.

## Extended programming model: the combiner
**Q:** In the word count example, what is the problem with emitting a tuple for each word?
**A:** **Unnecessary communication.**

**Q:** How could it be solved?
**A:** With a **combiner phase**.

- The **combiner runs in each mapper**.
- It has the **same interface as reduce**.
- The (key, value) pairs generated by a mapper are **sorted and fed to the combiner**.
- Pipeline: `Input (partitioned for mappers) → Map → Combiner → Partitioning / Shuffle / Sort by key → Reduce (same key)`

## Example (2) with combiner
| Mapper 1 after combiner | Mapper 2 after combiner |
|---|---|
| (B,2) (C,1) (D,2) (E,1) | (D,2) (A,2) (C,1) (B,1) |

Shuffle gives (A,[2]) (B,[2,1]) (C,[1,1]) (D,[2,2]) (E,[1]), and the reducers output (A,2) (B,3) (C,2) (D,4) (E,1).
**12 pairs shuffled without a combiner, 8 with one.** Same result, less network traffic.

A combiner is valid when the reduce function is **associative and commutative** (e.g. sum, max). This is the same idea as Spark's `reduceByKey` partial reduce. See [reduceByKey vs groupByKey](../lec04-spark-part2/02-spark-execution-model-lineage-dependencies.md#groupbykey-vs-reducebykey-why-gain-a-deeper-understanding).
